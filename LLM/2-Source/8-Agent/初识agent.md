*   **2023-2024**
    *   **关注大模型本身**
    *   哪个模型回答得更好

    ↓

*   **2025 起**
    *   **关注点外延到 Agent**
    *   自主调用工具，持续推进任务

    ↓

*   **2026 国庆前后**
    *   **走向消费端**
    *   Grok bot、Manus Cue、Meta Muse 等陆续亮相

这一趋势也迅速延伸到了消费端，**Personal Agent** 产品陆续亮相，与之相关的产品、平台和基础设施研发需求也在持续增加。
# 企业内部的转变

企业内部也在经历类似的转变，越来越多的公司开始将 Agent 引入研发、运营、客服等环节，Agent 已经逐渐成为日常工具链的一部分。

*   **研发**
    *   代码生成、代码评审
*   **运营**

*   **客服**

开发者除了编写业务逻辑，还需要**将内部系统封装成模型可调用的工具**，并将它们组织成能够**自主完成任务的** Agent。

# Agent 由什么组成

> **Agent ≈ LLM + Tool + Context + Agent Loop**

![](Pasted%20image%2020261110195713.png)
---

*   **LLM**
    *   理解任务、分析问题并做出决策
*   **Tool**
    *   读取文档、查询数据、调用系统和执行操作
*   **Context**
    *   保存用户指令、历史信息和任务状态，是模型每一轮决策的依据
*   **Agent Loop**
    *   按决策、执行、观察、调整顺序反复推进，直到完成任务

# ReAct 的思路

在正式开始课程之前，我们先大概用 50 行代码写出一个最简单的 Agent。让模型和工具配合完成任务，常用的方法是 **ReAct (Reasoning + Acting)**，也就是让推理和行动交替进行，每一轮由三步组成。

*   **01 思考 Thought**
    *   分析当前掌握了哪些信息、还缺什么
    ↓
*   **02 行动 Action**
    *   调用哪个工具、传什么参数
    ↓
*   **03 观察 Observation**
    *   程序执行工具后，把结果交还给模型

> 🔄 模型基于新的观察进入下一轮思考，如此循环，直到它认为可以直接回答

# 消息结构

实现 ReAct 的核心是维护一个 `messages` 列表，每轮把它完整发给模型。列表中的每条消息都有一个 role，承担不同的职责。

```json
[
  {"role": "system", "content": "你是导购助手……"},
  {"role": "user", "content": "蓝牙耳机和降噪耳机哪个更便宜？"},
  {"role": "assistant", "content": null, "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": {"name": "get_price", "arguments": "{\"name\": \"蓝牙耳机\"}"}
    }
  ]},
  {"role": "tool", "tool_call_id": "call_1", "content": "{\"name\": \"蓝牙耳机\", \"price\": 129}"}
]
```
# 每种 role 的职责

*   **`system`**（角色设定）
    *   设定 Agent 的角色和行为约束
    *   通常放在列表第一条，模型在整个循环中都会遵循。

*   **`user`**（任务）
    *   用户提出的任务
    *   整个任务的起点，Agent 循环围绕它反复推进，直到模型能够给出最终回答

*   **`assistant`**（Action）
    *   模型的回复，当它包含 `tool_calls` 时就对应 ReAct 中的 **Action**
    *   程序执行对应工具，并把消息追加回 `messages`，让模型记住自己做过的决策

*   **`tool`**（Observation）
    *   执行工具后回填的 **Observation**，必须通过 `tool_call_id` 与前面的调用一一对应，模型才知道这个结果属于哪一次调用
# 工具声明的字段

*   **`name`**
    *   模型调用时使用的工具名
*   **`parameters`**
    *   约束参数的结构
*   **`additionalProperties`**
    *   设为 false，禁止模型传入未声明的字段

---

> **`description`** 是写给模型看的，模型主要依据它判断这个工具能做什么、什么时候该用。

这里特意写明一次只查一个，是为了让模型对两个商品分别发起调用，而不是把两个名字拼在一个参数里。
# 代码实现

示例让 Agent 比较两个商品的价格。商品价格用本地字典模拟，避免依赖外部服务；system 提示词要求模型对每个商品分别调用工具，不要猜测。

> 你是导购助手。对每个商品分别调用工具查询价格，再进行比较，不要猜测。

*   把当前 `messages` 发给模型
    ↓
*   返回中有 `tool_calls` 吗？
    *   **没有**：模型已经得出最终回答，循环结束
    *   **有**：依次执行每个工具调用，以 role 为 tool 的消息回填，进入下一轮 ↺

主循环最多执行 5 轮，防止模型陷入无限工具调用。
