## 一、Agent 发展简史
![](Pasted%20image%2020261113092947.png)
让机器像人一样思考，并替人完成工作，是人类延续了数千年的梦想。从古希腊神话中的青铜巨人塔罗斯、中国古代《列子·汤问》中偃师制作的人偶，到达·芬奇设计的机械骑士，都体现了人类对智能机器的早期想象。

随着机械技术的发展，自动织布机、工业机械臂等自动化机器逐渐走进现实，开始代替人类完成重复性劳动。但这些机器只能按照预设程序执行任务，缺乏理解环境和自主决策的能力。

自然语言处理技术的进步，让人机交互有了新的形式。2011 年，Siri 智能语音助手问世，人们开始能够通过自然语言指挥机器查询天气、设置闹钟、播放音乐。不过，Siri 高度依赖预先定义的功能和流程，能够完成的任务比较有限。

2016 年，AlphaGo 战胜世界顶尖围棋选手李世石，展现了机器通过深度学习、强化学习和搜索算法，在复杂环境中自主制定策略和作出决策的能力。但这种智能仍然局限于围棋等特定领域。

2022 年，ChatGPT 的出现带来了新的突破，LLM 展现出强大的自然语言理解、内容生成和一定的推理能力，能够通过对话处理各种不同类型的任务。但早期的 ChatGPT 主要负责生成回答，难以直接操作外部系统完成任务。

2023 年起，主流模型 API 陆续原生支持工具调用，模型可以根据任务需要发起搜索、查询数据库、执行代码，再根据返回结果决定下一步操作，从生成回答走向执行任务。

在此基础上，Agent 已经广泛应用于各种场景。例如，客服 Agent 可以查询订单、处理售后问题；Research Agent 能够自主搜索资料、分析信息并生成研究报告；Coding Agent 则可以读取代码仓库、修改代码、运行测试，代表产品包括 Cursor、Claude Code 和 OpenAI Codex。
## 二、Personal Agent
![](Pasted%20image%2020261113093047.png)
2026 年下半年，Agent 的发展又进入了一个新的阶段，面向个人用户的 **Personal Agent** 陆续发布，代表产品包括：

- **Grok Bot**：2026 年 8 月发布，拥有持久化的云端计算机、浏览器、文件系统和终端，可以跨应用执行任务，还支持多个 Bot 协作和复用工作流程。
- **Meta Muse**：2026 年 9 月发布，运行在独立的 Muse Secure VM 中，能够使用浏览器、邮件等应用，主动规划和执行个人任务，并在后台持续工作。
- **OpenAI Dots**：2026 年 9 月发布，拥有独立的云端计算机和浏览器，可以连接个人电脑及外部应用，结合长期记忆持续处理工作，并主动跟进任务。
- **Claude Duet**：2026 年 10 月以研究预览形式发布，能够在云端虚拟机中执行任务，主动检查用户关注的信息、处理日常工作，并在关键操作前请求确认。

这些 Personal Agent 展现出一个共同的技术趋势：Agent 正在拥有自己的计算机和运行环境，从对话工具逐渐发展为能够独立工作的数字助手。

这与我们熟悉的对话式 AI 有着很大的区别。过去，我们向 ChatGPT 提出问题，等待模型返回答案；现在，我们可以直接把工作交给 Personal Agent，让它在自己的计算机中操作软件、调用工具、持续推进任务，直到交付最终结果。

课程的核心目标，就是让大家有能力从零实现一个类似的 Personal Agent，它能够理解指令、自主规划、操作软件、记住用户偏好，并在自己的运行环境中持续完成任务。

## 三、Agent = LLM + ？

要实现这样的 Personal Agent，首先要弄清楚 Agent 究竟是什么，以及它在 LLM 之外还需要哪些部分。
![](Pasted%20image%2020261113093106.png)
Agent 是指能够感知环境、围绕目标自主决策并采取行动的系统。回顾 Agent 的发展历程，我们会发现，Agent 并不是 LLM 出现后才诞生的概念，AlphaGo 这类能够感知局面、自主决策的系统同样可以视为特定类型的 Agent。只不过今天讨论的 Agent，通常指的是以 LLM 为核心构建的智能系统。

LLM 能够理解任务、生成内容，但单纯调用 LLM API，通常只能得到一段文本或结构化结果。例如，把项目情况描述给模型，它可以给出分析思路和建议，却无法直接读取项目文档、查询系统数据或修改项目状态。下面直接调用一次模型 API，让它评审本地的一份 PRD，请求中只给出文件名 `homepage_rec.md`。
```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="deepseek-flash",
    messages=[
        {"role": "system", "content": "你是 PRD 评审助手。"},
        {"role": "user", "content": "帮我评审一下 homepage_rec.md 这份 PRD，指出其中的问题。"},
    ],
)
print(response.choices[0].message.content)
```
我这边不能直接读取你本地/仓库里的 `homepage_rec.md` 文件，所以目前还无法逐条评审这份 PRD。  
请你把 PRD 正文粘贴过来，或上传可访问的文本；如果你希望我按首页推荐 PRD 标准来评审，也可以同时补充以下信息...

PRD 文件就在本地，但模型拿到的只有一个文件名，它无法自己打开文件读取内容，无论怎样回复，结果都只是一段文本。

要让模型读到这份 PRD，就需要把读取文件这类操作封装成 Tool 提供给模型，由模型判断什么时候调用、传入什么参数，再由程序执行并把结果返回给它。但真实任务往往不止一步，读完文档后，模型可能发现其中的数据判断缺少依据，需要查询业务数据核实，拿到数据后再决定是否继续查证。因此，还需要一套持续决策和执行的机制，模型决定下一步行动，系统执行相应的工具，再把执行结果反馈给模型，如此循环直到任务完成，这套机制就是 Agent Loop。

循环执行还带来了另一个问题，Agent Loop 的每一轮决策都是一次新的 API 调用，而模型不会保存之前调用的信息和状态，每次调用都相互独立，也就是说，模型本身并没有记忆能力。

下面连续发起三次调用，每次请求都带上同一条 system 消息；第一次在 user 消息中交代评审重点，第二次只发送一句追问，第三次把前面的对话连同追问一起发送。
```python
SYSTEM = {"role": "system", "content": "你是 PRD 评审助手。"}

# 每次请求都在消息前加上 system 消息
def chat(messages):
    response = client.chat.completions.create(model="deepseek-flash", messages=[SYSTEM] + messages)
    return response.choices[0].message.content

# 第一次调用：交代评审重点
first = [{"role": "user", "content": "接下来评审 PRD 时，请重点关注数据指标是否有依据。"}]
reply = chat(first)
print("第一次调用：", reply)

# 第二次调用：只发送新问题
question = {"role": "user", "content": "我刚才让你重点关注什么？"}
print("第二次调用：", chat([question]))

# 第三次调用：把前面的消息一起发送
history = first + [{"role": "assistant", "content": reply}, question]
print("第三次调用：", chat(history))
```
```text
第一次调用： 收到。接下来评审 PRD 时，我会把“数据指标是否有依据”作为重点检查项，尤其关注：
......
如果你愿意，也可以直接发 PRD 内容，我会重点帮你检查其中的数据指标是否站得住。

第二次调用： 在当前这段对话里，你还没有告诉我“重点关注”的内容；我目前能看到的是你刚发的这句话。
如果你指的是上一个会话或更早的上下文，这里没有显示。你可以把当时的要求再发一下，我可以按那个重点来评审。

第三次调用： 你刚才让我重点关注：**PRD 里的数据指标是否有依据**。
```
三次请求都带着同一条 system 消息，模型每次都知道自己是 PRD 评审助手，评审重点却只写在第一次调用的 user 消息里。第二次调用的请求中只有 system 消息和一句追问，模型无从得知第一次调用中交代过什么；第三次调用带上了前面的对话，模型才能据此作答。

换句话说，system 消息之所以始终生效，也只是因为每次请求都重新发送了它。Agent 的执行也是如此，每一轮决策前，系统都要把用户指令、历史消息和已有的工具结果重新组织好交给模型，它才知道任务进行到了哪一步、下一步该做什么。这些每一轮随请求交给模型的信息就是 Context，模型之所以能在多轮执行中记得前面发生过什么，靠的正是它。

因此，可以把 Agent 简单理解为 **Agent ≈ LLM + Tool + Context + Agent Loop**，其中各部分的职责如下：

- **LLM**：Agent 的决策核心，负责理解任务、分析信息、选择行动和生成结果；
- **Tool**：Agent 与外部世界交互的手段，例如读写文件、搜索网页、查询数据库、调用 API 或执行代码；
- **Context**：模型决策所依赖的信息，包括 system 消息、用户指令、对话历史、工具结果以及当前任务状态，每一轮决策前都要重新交给模型；
- **Agent Loop**：Agent 的核心控制机制，负责组织模型决策、工具执行和结果反馈，直到任务完成或需要人工介入。

这一组合让 AI 从单次问答发展为能够持续执行任务的系统。

关于 Agent 的定义，业界有很多不同的表达，其中比较流行的一种是 **Agent = LLM + Harness**。

LLM 负责理解任务和自主决策，Harness 则提供工具调用、上下文管理、执行循环、记忆和运行环境等能力，让模型能够与外部世界交互，并根据执行结果不断调整行动。

当然，也有人用 **Agent = LLM + Tools + Memory + Planning** 等公式来描述 Agent。虽然不同的表达强调的能力有所区别，但本质上都在描述同一件事，即如何让 LLM 与工具、上下文和执行机制协同工作，将模型的理解与决策能力转化为实际行动，最终完成用户交给它的任务。
## 四、Agent 的运行时
![](Pasted%20image%2020261113093422.png)
LLM + Tool + Context + Agent Loop 描述的是 Agent 的逻辑组成，但模型在每一轮决策中输出的只是一个工具调用请求，说明要调用哪个工具、传入什么参数，真正去读取文件、查询数据或执行代码的，是模型之外的程序。

如果只是读取一份本地文档，执行工具不过是调用一个函数；但 Agent 要在真实的文件系统、终端和浏览器中完成任务时，执行环节就会面临很多新的问题。工具可能超时或报错，需要把异常整理成模型能够理解的结果反馈回去；任务可能持续很长时间，中间的进度和状态需要保存下来，中断后还要能够恢复；修改文件、执行命令、发送邮件这类操作会直接影响外部环境，需要放在隔离的沙箱中运行并限制权限，关键操作前还要征得用户确认。

承担这些职责的基础设施就是 **Runtime**，它位于模型决策和结果反馈之间，负责实际执行工具、管理任务状态、处理异常和控制执行权限。前面介绍的 Personal Agent 拥有独立的云端计算机或虚拟机，有的还会在关键操作前请求用户确认，这些正是 Runtime 在产品层面的体现。

除 LLM 之外，Tool、Context、Agent Loop 和 Runtime 合起来，就是前面提到的 Harness。在这些基础能力之上，还可以进一步引入 Memory、RAG、Skill 等机制，让 Agent 能够利用历史经验、外部知识和预先封装的专业能力完成更加复杂的任务。
![](Pasted%20image%2020261113093435.png)
以 Coding Agent 为例，当用户要求修复一个 Bug 时，Agent 会先读取相关代码，分析可能的原因，再修改文件、运行测试，这些操作都由 Runtime 在真实的开发环境中执行。如果测试失败，它会根据错误信息继续调整代码，直到问题解决或遇到无法处理的情况。

这个过程可以概括为：**理解目标 → 决策行动 → 执行工具 → 观察结果 → 调整决策 → 完成任务**

其中最关键的是执行反馈形成的闭环，Agent 能够根据环境变化不断调整行动，而无须开发者提前规定每一个具体步骤。
## 五、LLM、Workflow 与 Agent 的区别

![](https://cdn.nlark.com/yuque/0/2026/png/87727/1792068018506-2dc0daf9-3820-447b-ace7-e68dc0a4afc5.png)
是否需要开发者提前规定每一个步骤，正是 Agent 与 Workflow 的分界。在实际开发中，LLM、Workflow 和 Agent 经常被一起讨论，但它们所代表的能力层次并不相同。

下面用同一个 PRD 评审任务，分别看看三种方式的写法。示例准备了两份 PRD 和几项业务指标，都用本地字典模拟，其中 `search_filter.md` 写明了数据来源和具体目标，`homepage_rec.md` 只说点击率偏低，没有给出任何数据。`read_doc` 按文件名返回文档内容，`query_metric` 返回指定指标的最新数据。
```python
DOCS = {
    "search_filter.md": """# 搜索结果页增加筛选栏
## 背景
根据 2026 年 9 月的搜索看板，搜索结果页的无点击率为 38%；在 12 位受访用户中，有 9 位提到找不到按价格和品牌筛选的入口。
## 方案
在搜索结果页顶部增加筛选栏，支持价格区间、品牌、发货地三个维度。
## 目标
上线一个月内，搜索结果页无点击率从 38% 降到 30%。
""",
    "homepage_rec.md": """# 首页推荐位改版
## 背景
首页推荐位的点击率偏低，不少用户反馈推荐内容不够相关。
## 方案
将推荐位从 4 个扩展到 8 个，并接入新的个性化推荐模型。
## 目标
推荐位点击率提升 20%。
""",
}

METRICS = {
    "搜索结果页无点击率": {"period": "2026-09", "value": "38%"},
    "首页推荐位点击率": {"period": "2026-09", "value": "6.2%", "trend": "近 3 个月在 6.0%～6.4% 之间"},
    "首页推荐位负反馈率": {"period": "2026-09", "value": "0.8%", "trend": "近 3 个月基本持平"},
}


def read_doc(name):
    return DOCS.get(name, f"找不到文档：{name}")


def query_metric(metric):
    return METRICS.get(metric, {"error": f"没有该指标：{metric}"})
```
### LLM 问答

**LLM 是基础模型能力**，开发者提供输入，模型根据上下文生成输出。例如，将一份 PRD 交给 LLM，让它分析需求中可能存在的问题。代码中由开发者读取 PRD、拼进 Prompt，再调用一次模型。`ask` 用 system 消息设定评审角色，user 消息给出具体任务，后面的 Workflow 和 Agent 也沿用同一个角色，三种写法只在执行过程上有区别。
```python
def ask(prompt):
    """调用一次模型，返回生成的文本。"""
    response = client.chat.completions.create(
        model="deepseek-flash",
        messages=[
            {"role": "system", "content": "你是 PRD 评审助手。"},
            {"role": "user", "content": prompt},
        ],
    )
    return response.choices[0].message.content


prd = read_doc("homepage_rec.md")
print(ask(f"评审这份 PRD，指出最多 3 个问题：\n{prd}"))
```
```text
1. **目标缺少完整指标口径与护栏指标**  
   “点击率提升 20%”需要明确基线、统计周期、计算方式、用户分群等。推荐位从 4 个扩展到 8 个后，单位 CTR 可能上升，但整体点击、用户停留时长、负反馈率可能下降，需要补充护栏指标。

2. **方案与问题之间的因果关系不够清晰**  
   用户反馈的核心是“推荐内容不够相关”，但方案除了接入新模型，还直接增加推荐位数量。增加展示数量不一定提升相关性，反而可能造成界面拥挤、注意力稀释。应更重点说明新模型如何解决相关性，以及扩展位置的验证依据。

3. **缺少实验设计与风险兜底机制**  
   PRD 未说明如何通过 A/B 实验验证效果，也未覆盖新模型的延迟、冷启动、准确率下降、性能影响等风险。建议明确灰度方案、回滚机制，以及不同人群下的评估指标。
```
### Workflow

**Workflow 是流程编排机制**，开发者提前设计好任务步骤，系统按照既定流程运行。例如，先提取 PRD 内容，再调用模型检查完整性，最后生成评审报告。即使流程中的节点使用了 LLM，整体执行路径仍然主要由开发者控制。下面把这三步写成一个函数，依次评审两份 PRD。
```python
def review(name):
    print("Step 1: 提取 PRD 内容")
    prd = read_doc(name)

    print("Step 2: 检查完整性")
    issues = ask(f"检查这份 PRD 的完整性，列出缺失或缺少依据的信息：\n{prd}")

    print("Step 3: 生成评审报告")
    return ask(f"根据以下检查结果，生成最多 3 条评审意见：\n{issues}")


for name in ["search_filter.md", "homepage_rec.md"]:
    print(f"===== {name} =====")
    print(review(name))
```
```text
===== search_filter.md =====
Step 1: 提取 PRD 内容
Step 2: 检查完整性
Step 3: 生成评审报告
基于提供的 PRD 检查结果，以下是提炼出的 3 条核心评审意见：

1. **补充功能规格细节与交互逻辑定义**
   当前文档缺乏开发与设计可执行的具体规则。需明确筛选维度的具体参数（如价格档位是固定还是自定义、品牌数据源及展示上限）、多维筛选的组合逻辑（AND/OR）、状态保持机制（返回/翻页后是否保留条件）以及空结果页的处理策略。建议通过“用户故事+验收标准”或详细的字段规格表来消除歧义。

2. **强化数据依据与目标设定的合理性论证**
   目前仅凭小样本定性调研支撑全局决策且 KPI 设定缺乏理论依据。需补充定量数据佐证痛点归因（排除排序算法等其他因素干扰），并提供竞品对标数据或漏斗模型测算，以解释为何无点击率能从 38% 降至 30%，确保目标设定的科学性与可达性。

3. **完善非功能性需求与发布运营计划**
   缺失性能指标、埋点体系及灰度策略。需定义后端检索的性能要求（如响应时间上限、大数据量处理方案），设计包含曝光、点击、转化等过程指标的完整埋点字典以便后续归因分析，并制定具体的 A/B 测试方案及分阶段灰度上线计划以降低风险。


===== homepage_rec.md =====
Step 1: 提取 PRD 内容
Step 2: 检查完整性
Step 3: 生成评审报告
基于该 PRD 处于概念阶段且缺乏落地细节的现状，以下是三条最关键的评审意见：

1.  **补充量化基线与护栏指标，确立可验证的目标体系**
    当前“CTR 提升 20%”的目标缺乏数据支撑且存在风险。需补充当前 CTR 的具体数值、行业基准及用户反馈的定量来源（如 NPS 评分分布），以明确问题严重性；同时必须定义**护栏指标**（如页面停留时长、跳出率、LCP 加载速度、后续转化率等），防止为追求点击率而损害用户体验或系统性能，并明确 A/B 测试的时间维度与分群预期。

2.  **细化交互逻辑与算法实现方案，消除技术执行盲区**
    PRD 对“8 个推荐位”的描述过于宏观，无法指导设计与开发。需明确 UI 布局规则（多端适配、卡片元素构成）、交互行为（负反馈机制、刷新策略）以及核心算法逻辑（输入特征、召回/排序策略、冷启动处理、去重规则）。此外，必须定义技术依赖风险及异常兜底策略（如算法超时时的默认展示内容），确保功能闭环。

3.  **完善非功能性需求与发布风控机制，保障上线稳定性**
    缺失性能约束、埋点规范及回滚计划是重大隐患。需补充具体的性能指标（如首屏加载时间上限、API 频率限制）和详细的埋点事件表（含曝光、点击、参数定义）；同时制定明确的灰度发布策略（流量比例、观察周期、全量标准）及快速回滚机制（开关配置、旧版切换流程），确保在出现 Bug 或数据负向时能迅速止损。
```
两份 PRD 走的是完全相同的三步，执行路径写在函数里，与 PRD 的内容无关。流程中没有查询数据这一步，面对 `homepage_rec.md`，Workflow 至多指出它缺少数据支撑；如果要核实数据，开发者就得在代码里加上查询步骤，并提前决定查哪个指标，而这一步对每份 PRD 都会执行。

### Agent

**Agent 则具有更高的自主决策能力**，开发者提供目标和可用工具，由模型根据任务进展决定采取哪些行动。例如，要求 Agent 评审 PRD，它可以自主读取文档、查询相关业务数据、识别信息缺失，并决定是否需要进一步调用工具。Agent 的写法里没有评审步骤，system 提示词只交代目标和边界。

```text
你是 PRD 评审助手。先读取文档；PRD 中的判断缺少数据支撑时，查询业务数据核实；最后给出最多 3 条评审意见。
```

工具声明中，`read_doc` 读取文档，`query_metric` 查询业务数据，参数用 `enum` 限定为已有的几项指标，`make_tool` 负责按 JSON Schema 生成声明。`run_agent` 就是前面介绍的 Agent Loop，每轮把 messages 发给模型，执行它请求的工具并回填结果，直到模型给出最终回答。

```python
tools = [
    make_tool("read_doc", "按文件名读取 PRD 文档全文", {"name": {"type": "string"}}),
    make_tool(
        "query_metric",
        "查询业务指标的最新数据，用于核实 PRD 中的数据判断",
        {"metric": {"type": "string", "enum": list(METRICS)}},
    ),
]
handlers = {"read_doc": read_doc, "query_metric": query_metric}

for name in ["search_filter.md", "homepage_rec.md"]:
    print(f"===== {name} =====")
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"评审 {name}"},
    ]
    run_agent(messages, tools, handlers)
```

三者的主要区别在于**由谁决定任务的执行过程**。直接调用 LLM 时，执行过程只有一次生成，输入什么、何时调用都由开发者决定；Workflow 的执行路径由开发者提前编排，模型只负责完成其中的节点；Agent 的执行路径则由模型在一定边界内根据任务进展动态决定。

不过，Workflow 与 Agent 并不冲突，在真实业务中，通常会使用 Workflow 控制确定性较强的环节，再由 Agent 处理需要自主判断的复杂任务。
## 六、Agent 开发的知识体系

Agent 开发通常不需要从头训练 LLM，开发者的主要工作，是围绕模型构建一套能够理解任务、访问外部环境、自主决策、执行操作，并可靠交付结果的软件系统。

从知识体系来看，Agent 开发可以划分为四个层次：
![](Pasted%20image%2020261113093716.png)
1. **Agent 基础原理。** 理解 Token、Context Window、模型 API、Temperature、Streaming、Function Calling 等基本知识，掌握 Prompt Engineering、Context Engineering 和 Agent Loop，能够从零开发一个最小 Agent。
2. **Agent 能力扩展。** 通过 Tool、MCP 连接外部系统，通过 Browser Use、Computer Use 操作网页和桌面软件，通过 RAG 和知识工程利用专业知识，通过 Memory 保存长期信息，通过 Skill 封装可复用的任务能力，让 Agent 从通用助手发展为具备专业能力的系统。
3. **Agent 架构与运行。** 掌握 Planning、Workflow、SubAgent、Multi-Agent 等复杂任务组织方式，理解 Runtime、Sandbox、远程运行环境、后台任务调度、任务状态管理和执行恢复等机制，让 Agent 能够稳定完成多步骤、长时间运行的任务。
4. **Agent 产品与工程化。** 通过 Evaluation、Observability、权限控制、安全机制、成本优化和前端交互等工程能力，将 Agent 从实验性的 Demo 发展为能够在真实业务环境中使用的产品。

这四个层次也构成了后续 Agent 开发课程的学习路线，**从理解模型如何工作，到构建 Agent 的行动能力，再到设计复杂的执行系统，最终交付可靠的 Agent 产品。**
