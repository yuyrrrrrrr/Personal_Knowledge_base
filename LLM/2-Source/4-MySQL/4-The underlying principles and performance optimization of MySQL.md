## 1. MySQL 架构与 SQL 执行流程

MySQL 逻辑架构可以划分为：

- 连接层：管理客户端连接、认证、线程和权限。
- 服务层：负责 SQL 解析、优化、执行、内置函数和复制相关能力。
- 引擎层：提供可插拔存储引擎接口。
- 存储层：负责数据文件、日志和磁盘交互。

SQL 执行的主要过程：

1. 连接器完成认证并建立会话。
2. 解析器对 SQL 进行词法和语法分析。
3. 优化器选择索引、连接顺序和执行策略。
4. 执行器调用存储引擎读取或修改数据。
5. 结果返回客户端；写操作还会涉及日志和事务提交。

- 不同 MySQL 版本的执行细节存在差异，应结合版本和实际执行计划分析。
- 权限检查、表元数据和引擎统计信息都会影响执行过程。

## 2. 存储引擎与数据文件

### InnoDB

- 支持事务、行级锁、外键、MVCC 和崩溃恢复。
- 使用聚簇索引组织数据，主键选择会影响数据存储和二级索引大小。
- 常见文件包括表空间文件、`ibdata`、redo log 和 undo log。

### MyISAM

- 不支持事务和行级锁，主要使用表级锁。
- 读取性能较好，但写入并发和崩溃恢复能力有限。
- 适合只读、历史兼容或特定导入场景，新项目通常优先使用 InnoDB。

### 表空间与数据文件

- `ibdata1` 可用于保存系统表空间、undo 或部分元数据，具体取决于配置。
- `innodb_file_per_table` 让 InnoDB 表拥有独立表空间文件。
- 表空间膨胀后不一定自动缩小，删除大量数据后可能需要重建表回收空间。
- 数据文件、redo log 和 binlog 应结合磁盘性能、可靠性和容量规划。

## 3. 索引数据结构与分类

### 为什么使用 B+ 树

- B+ 树具有较高扇出，树高低，适合磁盘页读取。
- 非叶子节点只保存键和指针，可以容纳更多索引项。
- 叶子节点通过链表连接，适合范围查询和顺序扫描。
- 相比哈希索引，B+ 树支持范围查询和排序。
- 相比红黑树，B+ 树高度更低，能减少磁盘 I/O。

### 索引类型

- 主键索引：聚簇索引，叶子节点保存完整行数据。
- 二级索引：叶子节点保存索引键和主键值。
- 唯一索引：保证索引列值唯一。
- 普通索引：不要求唯一。
- 组合索引：由多个列按顺序组成。
- 全文索引：用于文本检索，和普通 B+ 树索引语义不同。

### 聚簇索引与二级索引

- 聚簇索引决定数据行的物理组织方式。
- 二级索引查询到主键后，往往需要回到聚簇索引读取完整行，这个过程称为回表。
- 如果索引已经包含查询需要的字段，可以形成覆盖索引，避免回表。

## 4. 索引优化与失效场景

### 最左匹配

```sql
CREATE INDEX idx_a_b_c ON demo (a, b, c);
```

- 组合索引遵循最左匹配原则，查询条件应从索引最左列开始连续使用。
- 范围查询会中断后续列的索引利用能力，具体行为需结合优化器判断。

### 常见失效场景

- 在索引列上使用函数或表达式。
- 隐式类型转换，例如字符串列用数字比较。
- `LIKE '%abc'` 前置通配符。
- 使用 `OR` 且部分条件无法利用索引。
- 查询返回大量数据，优化器可能选择全表扫描。
- 数据分布和统计信息不准确，导致优化器误判。

### 优化策略

- 优先为高选择性、常用于过滤、连接和排序的列建立索引。
- 组合索引列顺序要结合查询模式设计。
- 避免重复索引和无用索引，索引会增加写入和存储成本。
- 使用覆盖索引减少回表，使用前缀索引控制长字符串索引大小。
- 通过 `EXPLAIN`、慢查询日志和实际数据验证效果。

## 5. 事务与 ACID

- `Atomicity` 原子性：事务中的操作要么全部成功，要么全部失败。
- `Consistency` 一致性：事务前后数据满足业务约束和一致性规则。
- `Isolation` 隔离性：并发事务之间相互隔离。
- `Durability` 持久性：事务提交后结果不会因普通故障丢失。

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

- 事务应尽量短小，减少锁持有时间和回滚成本。
- 需要明确异常回滚、重试和幂等策略。
- 大事务可能导致 undo、binlog 和主从延迟压力。

## 6. 隔离级别与并发问题

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 不可能 | 可能 | 可能 |
| 可重复读 | 不可能 | 不可能 | InnoDB 通过 MVCC 和锁机制尽量避免 |
| 串行化 | 不可能 | 不可能 | 不可能 |

- 脏读：读到其他事务尚未提交的数据。
- 不可重复读：同一事务中两次读取同一行结果不同。
- 幻读：同一查询条件两次读取得到的行集合不同。
- MySQL InnoDB 默认隔离级别通常是可重复读。
- 隔离级别越高，一致性越强，但并发吞吐和锁冲突通常越高。

## 7. MVCC 与日志机制

### MVCC

- MVCC 通过版本链和快照读提高并发读写能力。
- 隐藏字段、undo log 和 Read View 共同实现多版本可见性判断。
- 快照读读取历史版本，当前读会读取最新版本并加锁。

### undo log

- 保存数据修改前的版本，用于事务回滚和 MVCC。
- 长事务会延长 undo 版本保留时间，增加存储和清理压力。

### redo log

- 记录物理或逻辑变更，用于崩溃恢复和保证持久性。
- WAL 思想先写日志再刷数据页，降低随机写压力。

### binlog

- binlog 记录逻辑变更，用于复制、备份恢复和审计。
- redo log 属于 InnoDB 引擎层，binlog 属于 MySQL Server 层。
- 两阶段提交协调 redo log 与 binlog，保证崩溃恢复时日志一致。

## 8. 锁机制与死锁

- 表锁锁住整张表，开销小但并发能力弱。
- 行锁锁住索引记录，并发能力更强，但依赖索引命中。
- 共享锁 `S` 允许多个事务读取，排他锁 `X` 阻止其他事务读写。
- 意向锁用于表级和行级锁之间的协调。
- `Gap Lock` 锁定索引间隙，`Next-Key Lock` 结合记录锁和间隙锁。
- 无索引或索引失效时，行锁可能扩大为更大范围锁甚至表锁。
- 死锁是多个事务互相等待对方释放锁，数据库通常会检测并回滚其中一个事务。
- 降低死锁概率应统一访问顺序、缩短事务、控制批量更新和确保索引命中。

## 9. SQL 与表结构优化

- 避免 `SELECT *`，减少不必要的数据传输和回表。
- 合理使用连接，避免无索引连接和笛卡尔积。
- 子查询根据执行计划改写为连接或临时结果。
- 分页查询避免巨大 `OFFSET`，可使用游标或延迟关联。
- 字段类型应选择最小足够范围，减少存储和索引成本。
- 金额使用 `DECIMAL`，避免浮点误差。
- 适度反范式可减少连接，但必须控制冗余一致性。
- 批量写入应控制批次大小和事务长度。
- DDL 变更要评估锁、复制延迟、磁盘空间和回滚成本。

## 10. 配置、硬件与性能测试

- 优化前先通过慢查询、监控、`EXPLAIN` 和系统指标确认瓶颈。
- 连接数、线程缓存、缓冲池、日志大小和刷盘策略需要结合内存与业务评估。
- `innodb_buffer_pool_size` 通常是重要内存参数，但不应挤占操作系统和连接内存。
- CPU、内存、SSD、网络和磁盘 IOPS 都可能成为数据库瓶颈。
- 基准测试应使用接近生产的数据量、并发模型和查询分布。
- 压测同时观察吞吐、延迟、错误、锁等待、复制延迟和资源使用。
- 配置修改必须记录版本、原因、测试结果和回滚方式。
