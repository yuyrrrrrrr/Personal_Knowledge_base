## 1. 监控基础

- 监控目标包括系统可用性、性能、容量、错误率和业务状态。
- 常用指标分为计数器、瞬时值和可聚合统计值。
- 监控要覆盖宿主机、容器、中间件、数据库、网络和业务接口。
- 监控数据应带有时间戳、标签和来源，便于聚合与筛选。
- 指标采集频率需要权衡实时性、存储成本和系统开销。
- 只采集指标不建立基线和告警策略，无法形成有效监控。

## 2. CPU 监控

```bash
top
mpstat -P ALL 1
pidstat -u 1
```

- 关注用户态、内核态、等待 I/O、空闲和软中断占比。
- `load average` 表示可运行和不可中断任务的平均数量，需要结合 CPU 数量判断。
- 单个进程持续高 CPU 时，可使用 `pidstat`、`perf` 进一步定位。
- CPU 高不一定代表瓶颈，可能是正常计算、忙等、频繁上下文切换或内存回收。
- 排查时同时观察线程、调用栈、系统调用和 I/O 等待。

## 3. 内存监控

```bash
free -h
vmstat 1
smem -r
```

- `free` 查看总内存、已用、缓存、缓冲和交换空间。
- Linux 会利用空闲内存做文件缓存，不能把所有缓存都视为已占用。
- 关注可用内存、换页、缺页、OOM 和交换空间频繁读写。
- `vmstat` 可观察 `si`、`so` 和 `r`、`b` 等指标。
- 进程内存要区分虚拟内存、常驻内存和共享内存。
- 内存泄漏通常表现为常驻内存持续增长且无法回收。

## 4. 磁盘与 I/O 监控

```bash
df -h
du -sh /var/*
iostat -x 1
iotop
```

- `df` 关注文件系统容量和 inode 使用率，`du` 定位目录占用。
- `iostat -x` 观察设备利用率、队列深度、响应时间和吞吐量。
- `iotop` 查看进程级磁盘 I/O。
- 高 I/O 等待可能导致 CPU load 升高，但 CPU 实际并不繁忙。
- 磁盘故障、RAID 重建、日志暴增和数据库刷盘都可能造成 I/O 瓶颈。
- 清理文件前必须确认归属和影响，不能只依据目录大小直接删除。

## 5. 网络监控

```bash
ss -s
sar -n DEV 1
iftop
nethogs
```

- 关注带宽、连接数、丢包、重传、延迟和连接状态。
- `ss -s` 查看连接统计，`ss -tulnp` 查看监听端口。
- `sar -n DEV` 提供历史网络接口统计。
- `iftop` 按连接查看带宽，`nethogs` 按进程查看流量。
- 网络监控需要区分入口、出口、内部服务和公网链路。
- 告警阈值应结合正常流量曲线，而不是只使用固定数字。

## 6. 性能分析工具

- `top`、`htop`、`atop`：交互式系统资源查看。
- `vmstat`、`mpstat`、`iostat`、`sar`：系统性能统计与历史分析。
- `pidstat`：按进程查看 CPU、内存和 I/O。
- `perf`：采样分析 CPU、调用栈和性能事件。
- `strace`：跟踪系统调用，适合定位卡住或反复失败的程序。
- `lsof`：查看进程打开的文件、端口和句柄。
- 工具应组合使用，并结合日志、监控指标和业务现象判断。

## 7. Prometheus 与 Grafana

- Prometheus 采用拉取模型采集指标，适合云原生和动态环境。
- Exporter 把主机、数据库、中间件等指标暴露为 Prometheus 格式。
- PromQL 用于查询、聚合和计算监控指标。
- Grafana 用于构建仪表盘、趋势图和告警可视化。
- Zabbix 适合传统主机和网络设备监控，Nagios 适合基础可用性检查。
- 指标标签不宜无限增长，否则会造成高基数问题。
- 监控系统自身也需要高可用、容量规划和备份。

## 8. 告警与处理流程

- 告警规则应有明确阈值、持续时间、严重级别和恢复条件。
- 通知渠道可包括邮件、短信、企业微信、钉钉和电话。
- 必须抑制重复告警、抖动和级联告警，避免告警疲劳。
- 告警信息应包含对象、指标、当前值、阈值、时间和影响范围。
- 处理流程通常为确认、分级、止损、定位、恢复、验证和复盘。
- 告警恢复后应更新阈值或监控盲区，持续降低误报和漏报。
