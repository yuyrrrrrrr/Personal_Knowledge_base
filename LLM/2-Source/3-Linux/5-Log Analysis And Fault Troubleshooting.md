## 1. 日志基础与 /var/log

- 日志用于记录系统、服务、安全、应用和用户行为。
- 常见级别包括 `DEBUG`、`INFO`、`WARN`、`ERROR`、`FATAL`。
- `/var/log/` 是传统系统日志目录，常见文件包括 `syslog`、`messages`、`auth.log`、`secure`、`dmesg`。
- `dmesg` 查看内核环形缓冲区，常用于硬件、驱动、OOM 和文件系统问题。
- 服务日志可能由 `rsyslog`、`journald` 或应用自身管理。
- 日志应包含时间、级别、进程、请求标识和关键上下文。

## 2. journalctl

```bash
journalctl -u nginx
journalctl --since "1 hour ago"
journalctl -p err -b
journalctl -f
```

- `journalctl` 查询 systemd journal 日志。
- `-u` 按服务过滤，`-b` 查看本次启动日志，`-p` 按级别过滤。
- `--since`、`--until` 按时间范围查询，`-f` 实时跟踪日志。
- `-k` 查看内核日志，`-o json` 可输出结构化数据。
- journal 默认可能不持久化，生产环境应配置存储策略和容量限制。
- 服务启动失败时，应结合 `systemctl status` 和 journal 日志判断。

## 3. 日志轮转

```text
/etc/logrotate.conf
/etc/logrotate.d/
```

- `logrotate` 按时间或大小轮转、压缩和删除日志。
- 轮转策略通常包含 `daily`、`weekly`、`rotate`、`compress`、`delaycompress`。
- `copytruncate` 适合无法重开日志文件的程序，但存在少量丢失窗口。
- 应用日志应设置最大文件大小、保留数量和压缩策略。
- 日志增长过快时要先定位原因，不能只靠删除文件掩盖问题。
- 删除正在写入的日志前应确认文件句柄，避免空间未真正释放。

## 4. 文本分析三剑客

### grep

```bash
grep -n "ERROR" app.log
grep -Ev "DEBUG|INFO" app.log
```

- `grep` 按模式搜索文本，`-n` 显示行号，`-v` 反向匹配，`-r` 递归搜索。

### sed

```bash
sed -n '1,20p' app.log
sed 's/old/new/g' app.log
```

- `sed` 适合流式替换、删除、插入和按行范围打印。
- `-i` 会直接修改文件，执行前应先备份或先输出预览。

### awk

```bash
awk '{print $1, $9}' access.log
awk -F, '$3 > 100 {print $1}' data.csv
```

- `awk` 适合按列提取、统计、过滤和格式化输出。
- 可按字段、条件、累计变量和结束块进行聚合。
- 处理超大日志时应配合 `zgrep`、`zcat` 和流式管道。

## 5. 日志聚合与告警

- 单机日志适合直接搜索，多机环境需要集中式日志平台。
- `ELK` 由 Elasticsearch、Logstash、Kibana 等组件组成；现代方案也常使用 Filebeat 和 OpenSearch。
- 日志应先结构化，再建立索引、字段映射和查询模板。
- 告警规则可以基于错误关键字、错误率、延迟、日志突增和服务无日志。
- 日志中不得记录密码、令牌、身份证号和完整支付信息等敏感数据。
- 日志平台需要控制存储周期、访问权限、索引容量和查询性能。

## 6. 故障排查方法论

- 先确认影响范围、开始时间、用户现象和最近变更。
- 遵循“先止损、再定位、后修复、最终复盘”的顺序。
- 按网络、主机、系统资源、服务进程、配置、依赖和业务逻辑分层排查。
- 每次只改变一个变量，并记录命令、输出和时间线。
- 优先验证最容易且可逆的假设，避免同时进行大量修改。
- 复现问题时保留现场，避免重启或删除日志导致证据丢失。

## 7. 常见故障案例

- 系统负载过高：检查 CPU、内存、I/O、进程和等待队列。
- 磁盘空间满：检查 `df`、inode、日志、临时文件和大文件句柄。
- 服务无法启动：检查配置、端口、权限、依赖、状态和 journal。
- 网络不通：依次检查链路、IP、网关、DNS、路由、防火墙和目标端口。
- 应用响应慢：检查下游依赖、数据库、线程池、连接池和错误日志。
- 内存不足：检查 OOM、进程常驻内存、缓存、交换和容器限制。

## 8. 应急响应与复盘

- 明确应急负责人、沟通渠道、升级路径和操作权限。
- 优先止损和恢复服务，避免在压力下进行不可逆操作。
- 记录时间线、变更、命令、结果、影响和临时处置。
- 复盘应区分直接原因、根因、触发因素和放大因素。
- 后续行动要形成责任人、截止时间和验证标准。
- 更新监控、告警、预案、脚本和文档，避免同类故障重复发生。
