## 1. 零样本、单样本与少样本

- Zero-shot：只给出任务说明，不提供示例。
- One-shot：提供一个输入输出示例。
- Few-shot：提供多个示例，让模型学习类别、语气、格式和边界。
- 示例应覆盖主要情况、边界情况和容易混淆的情况。
- 示例数量并非越多越好，低质量或重复示例可能引入偏差。
- 示例顺序会影响结果，可把最典型和最难样例放在明确位置。
- 示例中的输入输出必须真实一致，不能包含错误示范。

```text
把用户反馈分类为：问题、建议、表扬。

输入：页面经常打不开
输出：问题

输入：希望增加导出按钮
输出：建议
```

## 2. 思维链

- 思维链（Chain of Thought）通过显式中间推理提高复杂任务表现。
- “让我们一步步思考”是常见零样本 CoT 提示。
- 少样本 CoT 通过示例展示推理步骤和最终答案模式。
- 数学、逻辑、规划和多条件判断通常能从分步推理中受益。
- 对简单事实查询使用 CoT 可能增加成本并诱发过度推理。
- 生产系统不应无条件暴露内部推理过程，应要求输出可验证的结论、依据和必要步骤。

```text
请逐步检查数量、单价和折扣条件，最后给出总价与计算依据。
```

## 3. 自洽性

- 自洽性（Self-Consistency）让模型多次独立推理，再对结果进行投票或比较。
- 它适合答案可枚举、可比较或可验证的任务。
- 同一问题从不同角度求解，可以发现偶然错误和不稳定结论。
- 多路径推理会增加 Token 成本和响应时间。
- 最终答案应通过规则、外部工具或人工复核确认。
- 多样性过高会让结果更随机，应在温度和采样策略上保持控制。

## 4. 输出控制

- 使用 JSON、XML、Markdown、CSV 或固定表格约束输出结构。
- 明确字段名、字段类型、必填项、枚举值和缺失值表示方式。
- 要求模型只输出结果，不添加解释、前后缀或 Markdown 代码块。
- 限制长度、条数、段落数和字数，避免无关扩展。
- 对内容质量要求可加入准确性、完整性、一致性和可读性标准。
- 结构化输出最好配合解析器、Schema 校验和失败重试。

```json
{
  "summary": "string",
  "risks": ["string"],
  "confidence": 0.0
}
```

## 5. 提示词模板

- 使用变量占位符复用任务说明、输入数据和输出规则。
- 模板应区分固定指令与动态内容，避免用户输入覆盖系统约束。
- 条件判断可以根据输入是否缺失选择不同处理路径。
- 循环结构适合批量处理多条记录，但应在应用层控制批次。
- 模板应版本化，支持测试、回滚和变更对比。
- 不把密钥、隐私数据和业务敏感规则硬编码进公开模板。

```text
任务：{task}
背景：{context}
输入：{input}
输出格式：{format}
约束：{constraints}
```

## 6. 高级推理技巧

- 思维树（Tree of Thoughts）探索多条候选路径并比较结果。
- 自我反思（Self-Reflection）要求模型检查错误、遗漏和不确定性。
- 迭代优化（Iterative Refinement）根据反馈逐步改进输出。
- 任务分解把复杂问题拆成可验证的子任务。
- 反向验证可以从结果反推是否满足原始条件。
- 多智能体或角色分工可通过评审、辩论和汇总提高覆盖度，但成本更高。
- 高级技巧应服务于准确率和可验证性，而不是增加提示词长度。

## 7. 提示词链接与迭代优化

- Prompt Chaining 把复杂任务拆成多个连续提示词，每个步骤输出作为下一步输入。
- 链式流程适合检索、提取、分析、生成和校验分离的任务。
- 每一步应定义明确输入输出，并在中间节点进行格式校验。
- 中间输出可以记录为日志，便于定位错误来源。
- 迭代优化应基于测试集和失败样例，而不是只看单次结果。
- 提示词版本应记录变更原因、指标和回滚条件。
