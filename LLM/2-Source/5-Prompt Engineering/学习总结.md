# Prompt Engineering 学习总结

## 1-Prompt Foundation

- 大语言模型基于上下文生成内容，具备文本、代码、分析和结构化输出能力，也存在幻觉、遗漏和概率性。
- 模型选择需要综合任务类型、上下文长度、速度、稳定性、隐私、可验证性和成本。
- Token 与上下文窗口决定输入输出规模，长上下文需要控制噪声、摘要和分层检索。
- `temperature`、`top_p`、`max_tokens` 等参数影响随机性、输出长度和生成成本。
- 提示词通常包含指令、上下文、输入数据和输出指示，应使用清晰、具体、可验证的约束。

## 2-Prompt Advanced

- Zero-shot、One-shot 和 Few-shot 通过示例数量和形式影响模型对任务边界的理解。
- 思维链适合数学、逻辑、规划和多条件任务，但会增加成本并可能产生过度推理。
- 自洽性通过多次推理和结果比较降低偶然错误，最终答案仍需外部验证。
- 输出控制通过 JSON、Schema、字段和长度约束提升可解析性与稳定性。
- 提示词模板、思维树、自我反思、迭代优化和 Prompt Chaining 适合处理复杂流程。

## 3-Domain-specific

- 内容创作应明确主题、受众、渠道、风格、结构和必须覆盖的事实。
- 代码生成应提供语言、版本、上下文和约束，生成后必须测试、审查和验证。
- 数据分析应明确指标、时间范围、维度和数据局限，并要求计算依据。
- 问答与客服提示词应基于给定资料，设置权限边界、升级人工条件和不确定性说明。
- 创意设计提示词应包含主体、环境、构图、风格和目标，同时避免直接复制受保护作品。

## 4-Optimization and Debugging of Prompts

- 迭代优化应建立基线、测试集和版本记录，每轮尽量只改变少量变量。
- A/B 测试和参数调整需要同时衡量准确性、格式合规率、延迟和成本。
- 提示词压缩与负面提示词可以控制长度和风险，但必须重新验证有效性。
- 常见问题包括不准确、不完整、格式错误、幻觉、不稳定和安全风险。
- 评估应从准确性、完整性、一致性、创造性和可用性出发，并结合自动规则和人工审核。

## 5-Project Practice

- 项目选题需要明确用户、场景、输入输出、成功标准、隐私和错误成本。
- 工程流程通常包含样本集、基线提示词、模型选择、结构化输出、校验和回归测试。
- 推荐项目包括文档问答、内容助手、代码助手、数据分析、客服、学习辅导和 Agent 工作流。
- 项目评估应同时关注质量、延迟、成本、解析成功率、用户反馈和失败原因。
- 交付需要包含程序、模板、配置、测试、日志、权限、安全和复盘记录。

## 回顾问题

1. 大语言模型的能力和主要局限性分别有哪些？
2. Token、上下文窗口、输出长度和模型成本之间有什么关系？
3. `temperature`、`top_p` 和 `max_tokens` 分别影响什么？
4. 一个完整提示词通常包含哪些结构，为什么要使用分隔符？
5. Zero-shot、One-shot 和 Few-shot 分别适合什么场景？
6. 思维链和自洽性为什么能提升复杂任务表现，它们有什么成本？
7. 如何控制模型输出为稳定、可解析的 JSON 或结构化数据？
8. 代码生成提示词为什么必须包含运行环境和验证要求？
9. 领域提示词如何减少幻觉、越权和高风险错误？
10. 提示词优化时如何设计 A/B 测试和评估指标？
11. 输出不准确、不完整、格式错误和幻觉分别应如何排查？
12. 一个完整的提示词工程项目应包含哪些交付和迭代环节？
