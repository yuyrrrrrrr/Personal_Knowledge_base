## 1. 大语言模型基础

- 大语言模型通过大规模文本训练学习语言模式和统计规律，根据上下文生成后续内容。
- 常见模型包括 `GPT`、`Claude`、文心一言、通义千问、Kimi 等。
- 模型能力包括文本生成、摘要、翻译、问答、代码生成和结构化提取。
- 模型可能产生幻觉、遗漏、偏见、格式错误和上下文偏移。
- 模型输出具有概率性，同一提示在不同时间或参数下可能产生不同结果。
- 提示词工程的目标是提高任务清晰度、结果稳定性、可验证性和使用效率。

## 2. 模型选择与能力边界

- 不同模型在推理、代码、长文本、多模态、中文表达和工具调用能力上存在差异。
- 选择模型时应关注任务类型、上下文长度、响应速度、稳定性、隐私和成本。
- 通用对话模型适合开放式任务，专用模型或工具适合结构化计算和检索任务。
- 模型知识存在截止时间限制，需要实时信息时应使用搜索、知识库或工具调用。
- 高准确率场景需要增加引用、校验、人工审核或确定性代码。
- 不应把模型的自然语言解释当作事实证据，应验证关键结论。

## 3. Token 与上下文窗口

- Token 是模型处理文本的基本单位，可能对应单词、子词、汉字或符号。
- 上下文窗口决定一次请求可以容纳的输入和输出总长度。
- 超出上下文范围时，内容可能被截断、摘要或拒绝处理。
- 长上下文不等于模型能同等关注每个位置，关键内容应放在清晰结构和高优先级位置。
- 输入越长通常成本越高、速度越慢，应删除无关内容和重复说明。
- 需要保留长期信息时，可使用摘要、检索、外部存储或分段处理。

## 4. 模型参数与使用成本

```json
{
  "temperature": 0.7,
  "top_p": 0.9,
  "max_tokens": 1000
}
```

- `temperature` 影响采样随机性，低值更稳定，高值更多样。
- `top_p` 控制候选词范围，通常不应与 `temperature` 同时大幅调整。
- `max_tokens` 限制最大输出长度，过小会导致回答被截断。
- `frequency_penalty`、`presence_penalty` 可影响重复和话题多样性。
- 成本由输入 Token、输出 Token、调用次数和模型价格共同决定。
- 优化成本应从提示词精简、缓存、模型分级和输出长度控制入手。

## 5. 提示词基本结构

一个清晰提示词通常包含：

- 指令：明确希望模型执行什么任务。
- 上下文：提供背景、目标、受众和约束。
- 输入数据：提供待处理内容，并使用分隔符隔离。
- 输出指示：规定格式、字段、长度和示例。

```text
你是数据分析助手。
请阅读下面的销售数据，提取异常情况。
要求：使用 JSON 输出，字段为 reason、evidence、action。

数据：
...
```

- 结构越清晰，模型越容易确定任务边界。
- 指令应说明目标、范围、输入来源和输出标准。
- 输入内容不完整时，应明确模型是否可以询问或必须给出假设。
- 输出要求应可验证，例如字段名、枚举值、长度和引用来源。

## 6. 基础编写技巧

- 使用清晰、具体、可执行的指令，避免“写得更好”这类模糊要求。
- 提供必要背景，但不要塞入与当前任务无关的信息。
- 使用标题、列表、代码块和三引号等分隔符组织输入。
- 明确指定输出格式、语言、语气、长度和目标读者。
- 设置约束条件，例如不得编造、必须引用输入、超出范围如何处理。
- 对复杂任务分步骤描述，并在关键步骤要求检查或汇总。
- 提供少量高质量示例，帮助模型理解预期模式。

## 7. 常见提示词模式

- 角色扮演：让模型从特定身份、专业视角或受众角度回答。
- 任务分解：把复杂目标拆成多个子任务和检查点。
- 示例引导：通过一个或多个输入输出示例说明期望。
- 步骤说明：要求模型按顺序分析、计算、验证并给出结论。
- 约束式输出：规定 JSON、表格、Markdown 或固定字段。
- 反向校验：要求模型检查遗漏、矛盾和不确定信息。

```text
任务：把会议记录整理为行动项。
步骤：
1. 提取负责人和截止时间。
2. 标记缺失字段。
3. 只输出 Markdown 表格。
```
