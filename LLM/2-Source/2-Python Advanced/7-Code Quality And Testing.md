## 1. 代码规范与可读性

- 遵循 `PEP 8`，使用一致缩进、命名和导入顺序。
- 函数与类保持单一职责，减少超长函数和深层嵌套。
- 名称应表达业务含义，避免无意义缩写和模糊变量。
- 使用格式化与静态检查工具统一风格。
- 常见工具包括 `black`、`ruff`、`flake8`、`isort` 等。
- 规范工具的作用是减少低级分歧，不能替代良好的结构设计。

## 2. 类型注解与静态检查

```python
def add(a: int, b: int) -> int:
    return a + b

names: list[str] = ["Alice", "Bob"]
```

- 类型注解说明参数和返回值预期类型，提高编辑器提示和可读性。
- Python 运行时通常不会自动强制检查类型注解。
- `list[str]`、`dict[str, int]`、`str | None` 是现代类型写法。
- `Any` 应谨慎使用，`Optional` 或 `| None` 更适合表达可空值。
- `mypy`、`pyright` 等工具可以执行静态类型检查。
- 注解应与实际行为保持一致，避免把错误类型隐藏起来。

## 3. 单元测试基础

```python
def add(a, b):
    return a + b


def test_add():
    assert add(1, 2) == 3
```

- 单元测试验证最小可测试单元的行为。
- 测试应覆盖正常路径、边界条件和异常路径。
- 测试名称应表达场景和预期结果。
- 测试之间应相互独立，不依赖执行顺序和外部可变状态。
- `unittest` 是标准库测试框架，适合需要类式组织的项目。
- 测试失败时应提供清晰、可定位的断言信息。

## 4. pytest 使用

```python
import pytest

@pytest.mark.parametrize(
    ("value", "expected"),
    [(1, 1), (2, 4), (3, 9)],
)
def test_square(value, expected):
    assert value ** 2 == expected
```

- `pytest` 可以直接发现 `test_*.py` 和 `test_*` 函数。
- 普通 `assert` 即可编写断言，失败信息通常足够清晰。
- `fixture` 用于准备和清理测试依赖。
- `parametrize` 适合用多组数据验证同一逻辑。
- `pytest.raises()` 用于验证代码抛出预期异常。
- `pytest -q` 适合简洁运行，`-k` 和 `-m` 可筛选测试。

## 5. 测试设计与 Mock

- 优先测试外部可观察行为，而不是实现细节。
- 对边界值、空输入、重复调用和异常输入进行重点覆盖。
- 测试文件读写、网络和数据库时，可隔离为临时目录、假实现或测试容器。
- `unittest.mock` 或 `pytest-mock` 可以替换外部依赖。
- Mock 应验证交互是否必要，避免测试被过度模拟代码绑架。
- `coverage` 可以统计执行覆盖率，但高覆盖率不等同于高质量测试。
- 测试应先保证稳定性，再考虑追求覆盖率数字。

## 6. 调试与日志

- 先复现问题，再缩小输入范围和调用路径。
- 阅读完整堆栈，确认异常最早出现的位置。
- `breakpoint()`、`pdb` 和 IDE 调试器适合观察运行时状态。
- 日志应使用合适级别：`DEBUG`、`INFO`、`WARNING`、`ERROR`、`CRITICAL`。
- 不要用大量临时 `print()` 替代持久日志。
- 异常日志应保留堆栈和关键上下文，但避免记录密码、令牌等敏感信息。

## 7. 文档、重构与质量流程

- 公共模块、类和函数应提供简洁文档字符串。
- README 应说明项目用途、安装方式、运行方式和测试方式。
- 重构是在不改变外部行为的前提下改善内部结构。
- 重构前应具备测试保护，重构后运行完整测试。
- 持续集成可以自动执行格式检查、静态检查、测试和覆盖率报告。
- 提交前检查未使用导入、调试代码、敏感配置和无关改动。
