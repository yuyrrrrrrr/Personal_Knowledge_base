## 1. 个人项目实战

- 初始化仓库并确定默认分支、目录结构和基础 README。
- 配置忽略规则，排除密钥、缓存、依赖目录和构建产物。
- 按功能拆分提交，保持提交信息清晰可搜索。
- 使用分支开发新功能，合并前检查差异和测试结果。
- 使用标签记录发布版本，并维护变更日志。
- 同时维护本地仓库和远程备份，避免单点丢失。

## 2. 团队协作项目实战

- 团队需要明确主分支、开发分支、功能分支和发布分支策略。
- 每个任务使用独立分支，并在 Pull Request 中说明变更范围。
- 统一提交信息和代码审查规则，减少沟通成本。
- 合并前更新目标分支、解决冲突并运行完整测试。
- 保护主分支，禁止直接推送和绕过审查。
- 发生紧急故障时使用热修复分支，并在修复后回并到其他长期分支。

## 3. 开源项目贡献实战

- 先阅读 README、CONTRIBUTING、Issue 模板和行为准则。
- 从文档、测试、简单 Bug 或标记为 `good first issue` 的任务开始。
- Fork 仓库并配置 `upstream`，保持本地分支与上游同步。
- 提交前运行项目要求的格式化、测试和静态检查。
- Pull Request 应保持窄范围，说明问题、方案和验证方式。
- 根据审查意见追加提交，避免直接覆盖讨论历史。
- 贡献过程中保持沟通，尊重维护者和其他贡献者。

## 4. 分支与发布流程

```bash
git switch -c release/1.2
git tag -a v1.2.0 -m "release v1.2.0"
git push origin release/1.2
git push origin v1.2.0
```

- 发布分支用于冻结功能、修复缺陷和准备发布说明。
- 发布前应确认版本号、依赖、构建产物、文档和回滚方案。
- 标签应指向经过验证的提交，发布后避免随意移动或重建。
- 发布后把必要修复回并到主开发分支。
- 版本号推荐遵循语义化版本规则。
- 发布流程应可重复、可审计并具备失败处理方式。

## 5. CI/CD 与质量门禁

- CI 在提交或 Pull Request 阶段执行测试、构建、Lint 和安全扫描。
- CD 根据环境执行发布、审批、灰度和回滚流程。
- 流水线应缓存依赖但保证缓存不会掩盖配置错误。
- 重要分支应要求 CI 通过、审查通过和冲突解决后再合并。
- 发布凭据应通过 Secrets 或密钥管理服务提供，不能提交到仓库。
- 失败流水线应保留日志、构建产物和足够的诊断信息。

## 6. 项目复盘与规范沉淀

- 复盘提交质量、分支生命周期、冲突频率和发布失败原因。
- 将重复问题转化为模板、Hook、CI 规则或文档。
- 维护常用命令、故障排查、发布和回滚手册。
- 统一团队术语和平台操作，减少平台专有差异带来的误解。
- 定期清理远程分支、过期标签、失效权限和长期未合并分支。
- Git 流程的目标是提升协作效率和交付质量，而不是追求形式复杂。
